# Speech Sculptor — процесс развития (mini-pipeline)

Этот процесс используется **только по явной команде владельца**, например: «Используй пайплайн развития для этой задачи». Обычные вопросы и мелкие правки не требуют полного цикла. Наличие этого файла не означает разрешения на самостоятельные изменения, слияния или релизы.

## Как поставить задачу

Достаточно трёх строк:

```text
Используй пайплайн развития.
Задача: [что хочу получить и зачем]
Результат: [что должен видеть или делать пользователь]
```

Ссылку на репозиторий и примеры можно добавить по желанию, если контекст уже известен.

## Этапы

1. **Аудит:** изучить актуальную ветку `main`, документы, код, реальные ограничения, существующие Issues и релизы. Не считать устаревшие номера версий доказательством текущего состояния.
2. **Постановка:** короткая задача GitHub Issue: проблема → пользовательский сценарий → границы → проверяемые критерии. Приоритет P0/P1/P2 с обоснованием.
3. **План:** выбрать минимальное изменение, поискать проверенное open-source решение при необходимости, указать файлы, риски, зависимости и способ проверки. Для сложной задачи сначала согласовать границы.
4. **Разработка:** отдельная ветка от актуального `main`, небольшие коммиты, без ненужного рефакторинга. Не трогать пользовательские данные и секреты.
5. **Проверка:** выполнить подходящие автоматические тесты и отдельно сквозной пользовательский сценарий. Непроверенное отметить «не проверено», не заменять реальные данные синтетическим демо.
6. **Pull Request:** заполнить шаблон PR, приложить фактические результаты тестов, ограничения, способ отката. Владелец рассматривает и решает, сливать ли изменения.
7. **Релиз:** только отдельно согласованный выпуск по существующим правилам проекта. Проверить установку и обновление на целевом устройстве.

## Определение готовности

Задача **готова к рассмотрению**, если критерии воспроизводимы, ограничения задокументированы, изменения изолированы в PR, а тесты не представлены как более сильное доказательство, чем они есть. «Есть код» ≠ «есть работающая установленная версия».

## Проверка именно этого проекта

- `python3 scripts/check_source.py` проверяет структуру исходников, но не работу импорта.
- На macOS runner используются `macos-build.yml` и регрессии из `Tests/`; для аудио — `bash scripts/test_audio_pipeline.sh`.
- Отдельно нужен ручной запуск .app на Mac: запись, импорт короткого и длинного M4A, разрешения, отмена и экспорт/история.

## Документы и выпуск

- `PRODUCT.md` — смысл и ограничения; `DESIGN.md` — дизайн; `QA_REPORT.md` — границы экспериментальных метрик; `ROADMAP.md` — дальнейшие цели.
- Если README и фактическая версия релиза различаются — зафиксировать расхождение и проверять репозиторий/сборку, не угадывать версию.

**Особое внимание:** `publish-release.yml` реагирует на push в `main` и может автоматически создать публичный релиз. Нельзя сливать PR с изменённой версией без проверки этого эффекта.
