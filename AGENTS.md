# Инструкции ИИ-разработчику — Speech Sculptor

## Продукт и рамки
Нативное macOS-приложение на SwiftUI для локальной записи, импорта и анализа русской речи. Пользовательский цикл: запись/импорт → разбор → понятные рекомендации → повтор → сравнение. Основные ориентиры: `PRODUCT.md`, `DESIGN.md`, `QA_REPORT.md`, `README.md`; последний документ может отставать от GitHub Releases.

## Карта проекта
- `Sculptor/` — SwiftUI, сервисы записи, импорта и анализа;
- `Tests/` — регрессии обработки аудио, контекста, метрик, качества;
- `scripts/` — структурная проверка, синтетические аудиофикстуры;
- `project.yml` — XcodeGen, macOS 14.2+, Swift;
- `.github/workflows/macos-build.yml` — тесты и сборка на macOS;
- `.github/workflows/publish-release.yml` — публикация GitHub Release при push в main (отдельно учитывать риск автоматической публикации).

## Безопасные изменения
- Сначала читать код и документы, затем минимальная правка. Существующие возможности, историю, дизайн и приватность сохранять.
- Аудиофайлы, расшифровки, API-ключи и личные сведения не добавлять в репозиторий и журналы.
- Локальное распознавание — режим по умолчанию; сетевые провайдеры только по явному действию пользователя. Не обещать гарантированного offline Apple Speech на каждом Mac.
- Не называть ориентировочные акустические метрики диагнозом или объективной оценкой эмоций.
- Отдельно проверять импорт M4A/MP3/WAV/CAF/AIFF, разрешения микрофона и Speech, длинные записи, отмену и ошибки.

## Тестирование и релизы
- Быстрая статическая проверка: `python3 scripts/check_source.py`.
- macOS regression: `bash scripts/test_audio_pipeline.sh` и другие команды из `macos-build.yml` (Swift, ffmpeg, Xcode нужны только для соответствующих проверок).
- CI-сборка и синтетические тесты **не заменяют запуск .app на Mac** с импортом и записью.
- Перед любым слиянием проверять эффект `publish-release.yml`: push в main может запустить выпуск; PR сам по себе не является разрешением на публикацию.
- Не менять версии, теги, релизы и код подписи без отдельной задачи.

## Работа с запросами
Полный процесс `DEVELOPMENT.md` использовать **только при явном запросе владельца**. По такой задаче: Issue/критерии → план → отдельная ветка → тесты → PR. Не сливать PR и не выпускать версию без отдельного поручения.
